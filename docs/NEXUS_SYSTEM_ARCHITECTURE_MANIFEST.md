### 1. Multi-Tenant Scoping Boundaries
To protect tenant privacy, NEXUS ERP enforces two boundary isolation layers:
* **Global Field Scoping (Root Collections)**: Collections like `products` (master inventory), `users`, and `audit_logs` are placed at the root level. Every query must include:
  `where("companyId", "==", currentCompanyId)`
* **Isolated Subpath Scoping (Transaction Collections)**: High-frequency transaction ledgers (e.g. `purchase_orders`, `quotations`, `stock_movements`, `sales_orders`) are nested within the company document:
  `/companies/{companyId}/purchase_orders/{poId}`
  This guarantees database-level isolation even if a client query lacks a filter.

### 2. Atomic ID Generation Engine (`idService`)
Sequential document IDs must never collide or jump numbers, even under high concurrent loads. The system uses a Firestore transaction to increment a scoped counter record:
* **Storage Path**: `/counters/{companyId}_{typePrefix}-{yy}` (e.g. `counters/COMP-A_PO-26`)
* **Prefix Protocols**:
  * `SKU`: Formatted as `SKU-[MNEMONIC]-[5-digit SEQ]` (e.g., `SKU-NET-00001`). Mnemonic is generated by extracting the first 3 letters of the category name (translated to English/Romanized).
  * `PRJ`: Formatted as `PRJ-[YY]-[MNEMONIC]-[4-digit SEQ]` (e.g., `PRJ-26-HOS-0001`).
  * `PO` / `QT` / `SO`: Formatted as `[PREFIX]-[YYMM]-[4-digit SEQ]` (e.g., `PO-2605-0012`).
* **Atomic Mutation Logic**:
  ```typescript
  // Core mechanism inside runTransaction
  const counterRef = doc(db, "counters", scopedCounterId);
  const nextSeq = (counterSnap.data().seq || 0) + 1;
  transaction.set(counterRef, { seq: nextSeq, year: yy, companyId: companyId }, { merge: true });
  return nextSeq;
  ```

### 3. Server-Side Security Rules (`firestore.rules`)
All database access is checked on the server using authenticated user claims:
* **belongsToCompany(companyId)**: Validates that the active user's secure token contains the target `companyId`.
* **Lock by Default**: All wildcards are locked (`allow read, write: if false;`).
* **Admin Gated Mutations**: Deletion of master data requires `ADMIN` or `SUPERADMIN` status.
* **Immutable Logs**: Document edits or deletions are strictly blocked in the `/audit_logs` collection.

## 📦 PART 2: COMMERCIAL & INVENTORY RESOURCE FLOWS

### 1. Inventory Stock Status Allocation
To support advanced Sales and Operations Planning (S&OP), stock levels for any SKU are tracked in three states:
* **OnHand (`qty_on_hand`)**: The physical quantity located inside the warehouse shelves.
* **Reserved (`qty_reserved`)**: Stock committed to active Sales Orders (`SO`) or assigned to uncompleted Projects.
* **Available (`qty_available`)**: Stock ready for sales or allocation. Calculated dynamically as:
  $$\text{qty\_available} = \text{qty\_on\_hand} - \text{qty\_reserved}$$

```
   [Purchase Order] ---> [Goods Receipt] ---> OnHand Stock (+1) / Available Stock (+1)
                                                    |
   [Sales Order / Project] ------------------------> Reserved Stock (+1) / Available Stock (-1)
                                                    |
   [Site Dispatch / Completion] ------------------> OnHand Stock (-1) / Reserved Stock (-1)
```

### 2. Weighted Average Cost (WAC) Algorithm
Inventory cost accounting uses the Weighted Average Cost (WAC) model. The unit cost of a product is updated immediately when a new batch of goods is received (Goods Receipt Note):

$$\text{Cost}_{\text{New WAC}} = \frac{(\text{Qty}_{\text{OnHand}} \times \text{Cost}_{\text{Current WAC}}) + (\text{Qty}_{\text{Received}} \times \text{Cost}_{\text{Purchase Unit}})}{\text{Qty}_{\text{OnHand}} + \text{Qty}_{\text{Received}}}$$

All Gross Profit (GP) calculations and Project budgets reference the snapshotted WAC value of materials to maintain margin integrity.

### 3. Project Hub & The Quotation Bridge
* **Dual-Catalog Picker**: Within the project modal, available warehouse items are displayed in a left-hand split catalog, divided into **📦 อุปกรณ์ (Standard Warehouse SKUs)** and **⚡ ชุดงานติดตั้ง (Pre-configured Installation Packages/Kits)**.
* **Labor Card Pricing Engines**:
  * **Lump-sum (เหมารวม)**: Fixed service pricing.
  * **Per Point (คิดตามจุด)**: Dynamic service pricing linked to a master material SKU, calculating labor cost based on number of points, technician rates, and GP margins.
* **Kit Editor Firestore Sync**: Custom labor setups can be grouped as a single package, evaluated via the **Profit Rainbow Panel**, and saved to the `/products` collection under category `"Kit"` with field `companyId`. These items immediately reload in the left-hand catalog without a browser refresh.
* **Zap Bridge**: Clicking **ออกใบเสนอราคา (QT) ⚡** pulls all material and service items from the project, maps them to a flat quotation schema, closes the project dashboard, and launches an unlocked `QuotationModal` (`isLocked = false`) for further adjustments.

## 📒 PART 3: Ledger Accounting & Audit Trails

### 1. Double-Entry General Ledger (GL) Postings
NEXUS ERP translates physical stock movements and procurement actions into double-entry accounting records inside the `/journal_entries` collection:
* **Receiving Goods (Receipt Note)**:
  * `DEBIT`: Inventory Asset (11500)
  * `CREDIT`: Accounts Payable (21100)
* **Sales / Project Delivery (Invoice Generated)**:
  * `DEBIT`: Accounts Receivable (11300)
  * `CREDIT`: Sales Revenue (41100)
  * `DEBIT`: Cost of Goods Sold - COGS (51100)
  * `CREDIT`: Inventory Asset (11500)
* **Balance Constraint**: Debits must equal Credits for every transaction. Balanced ledgers are guaranteed using a Firestore transaction:
  $$\sum \text{Debits} = \sum \text{Credits}$$

### 2. Logical Soft-Delete Policy
No transactional data or master SKU records are hard-deleted. To preserve database audit trails, deletions set `isDeleted: true`. All queries must filter using `where("isDeleted", "==", false)`.

### 3. Immutable Audit Trails
Every mutation (Create, Update, Delete) is logged via the `auditService` inside the `/audit_logs` collection. The log records:
* An operation label (`action: 'CREATE' | 'UPDATE' | 'DELETE'`)
* The target module (`module: 'INVENTORY' | 'SALES' | 'PROJECTS' | 'FINANCE'`)
* The state difference (`changes: { before, after }`)
* Operator metadata (User UID, timestamp, IP address, and browser user agent)

## 🧠 PART 4: NEXUS INTELLIGENCE AI ENGINE

The **Intelligence Hub** integrates **Genkit 1.x** and **Gemini 2.5 Flash** to provide predictive insight and automated data mapping:

```
  [Technician Receipt] ---> [Gemini 2.5 Flash OCR] ---> Extract Amount & Merchant
```

### 1. Expense Auto-Mapping (`analyzeExpenseOCR`)
Technicians upload field receipts directly. The AI processes the image and extracts the merchant, total amount, and billing category. It cross-references the employee's calendar and active GPS coordinate history to automatically suggest the correct project ID:
```typescript
interface OCRResult {
  amount: number;
  merchant: string;
  category: 'Materials' | 'Logistics' | 'Subcontractor' | 'Other';
  predictedProjectId: string;
  isAsset: boolean;
  reasoning: string;
}
```

### 2. Smart Asset Serial Tagging (`detectAssetRequirement`)
The AI monitors inventory arrivals and automatically flags high-value networking gear (e.g. Switches, Routers, UPS units) that require serial number tracking. It suggests an auto-formatted prefix (e.g., `NXI`) and prompts the warehouse team for serial numbers.

### 3. Proactive Warranty Checks & MA Generation
The system scans Serial Number entries daily. When an active asset is found with a warranty expiry date less than 30 days away, the system:
1. Flags the item in the CRM sales queue.
2. Auto-drafts a tailored Maintenance Agreement (MA) Proposal containing calculated support rates based on the asset category.

## 📐 PART 5: THE PSG UI PROTOCOL V3.1

All elements of the user interface are designed under strict guidelines to maintain premium aesthetics, readability, and data density.

### 1. Sizing, Dimensions, and Curves (PSG Compact Standards)
* **h-9 Standard Sizing**: Buttons, input boxes, dropdown selectors, and tabs are locked at a height of **36px (`h-9`)** to maximize screen real estate.
* **px-6 Sizing Standard**: Action buttons and interactive triggers use a horizontal padding of **`px-6` (24px)** for clean visual weight.
* **Capsule Curves**: All active controls use a **`rounded-full`** Pill shape.

### 2. Typography & Readability (PSG Non-Italic Rule)
* **0% Italic Policy**: **Italic text is prohibited across the entire ERP system**. All alphanumeric strings, pricing labels, and codes must use standard sans-serif weights for clean legibility.
* **Precision Monospace**: Monospace fonts are enforced for numerical values, document reference IDs, and transaction hash codes to keep columns aligned.
* **High Contrast Colors**: Low-contrast text elements on dark backgrounds are upgraded to high-contrast values (minimum `text-white/60` or `text-white/80`) to ensure text stands out.
* **Neon Glassmorphic Design**: High-fidelity surfaces use a neon-glow border combined with backdrop glass blur classes:
