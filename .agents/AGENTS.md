- เมื่อผู้ใช้สั่งให้ใช้ "ตารางอัจฉริยะ" ให้ประยุกต์ใช้คอมโพเนนต์ตารางที่มีความสามารถขั้นสูง (เช่น DocumentItemsTable) โดยต้องดึงรูปแบบ UI มาตรฐานมาใช้ทั้งหมด (ขนาดตัวอักษร, dropdown, ปุ่มเพิ่ม/ลดจำนวนในช่องกรอก, และลูกเล่นอื่นๆ) รวมถึงต้องวิเคราะห์ว่าตารางนั้นถูกนำไปใช้กับ "ข้อมูลอะไร" เพื่อตั้งชื่อหัวคอลัมน์และปรับแต่งการแสดงผลที่เกี่ยวกับฐานข้อมูลนั้นๆ และดึงมาเฉพาะข้อมูลที่จำเป็นต้องแสดงตามหน้าที่ของตาราง (เช่น การซ่อนคอลัมน์ หรือเปลี่ยนชื่อคอลัมน์ให้เข้ากับบริบท)
- **การปรับ UI และฟีเจอร์ต่างๆ ของตารางหลังจากนี้ ให้บันทึก/นำไปอัปเดตเป็นค่ากลาง (Central standard) ของคอมโพเนนต์ "ตารางอัจฉริยะ" (`DocumentItemsTable`) เสมอ** เพื่อให้ทุกหน้าที่เรียกใช้ตารางนี้ได้รับการอัปเดตฟีเจอร์และ UI ไปในทิศทางเดียวกันทั้งหมด- **มาตรฐานฟีเจอร์และ UI ของตารางอัจฉริยะ (`DocumentItemsTable`)** ที่ต้องยึดเป็นค่ากลางเสมอ:
  1. **การควบคุมแถวและเค้าโครง (Row Management & Layout)**:
     - **ความบางขั้นสุด (Extreme Compactness):** แถวต้องมีความกะทัดรัด บีบ Padding ลงต่ำสุด (หัวตาราง `py-2`, แถวข้อมูล `py-1 min-h-[36px]`) เพื่อให้แสดงข้อมูลได้มากที่สุดในจอเดียว
     - **ขนาดคอลัมน์ตายตัว (Strict Widths):** เลิกใช้ระบบ Grid `col-span` แต่ให้จัดแถวด้วย `flex gap-2` และล็อคความกว้างตายตัวของคอลัมน์ตัวเลข/รหัส (เช่น `w-12`, `w-36`, `w-20`, `w-28`) โดยให้เฉพาะคอลัมน์ "ชื่อรายการ" สามารถขยายยืดหยุ่นได้ (`flex-1`)
     - แถวที่ไม่ได้โฟกัส (Inactive) ต้องถูกพับเก็บเสมอ และเมื่อคลิกที่อื่นต้องยกเลิก Active
     - หากแถวที่เพิ่มใหม่ไม่มีการคีย์ข้อมูล (ว่างเปล่า) เมื่อเสียโฟกัสให้ลบแถวนั้นทิ้งอัตโนมัติ
     - **เมื่อกดเพิ่มรายการใหม่ หน้าต่างค้นหาจะไม่เด้งขึ้นมาเปิดเองโดยอัตโนมัติ** (ไม่ใช้ setTimeout focus) ต้องรอให้ผู้ใช้คลิกเข้าไปพิมพ์เอง
  2. **ช่องกรอกข้อมูล (Inputs & Controls)**:
     - **การเชื่อมต่อฐานข้อมูลตรง (Tenant Isolation & Performance):** ช่องค้นหารหัส/ชื่อสินค้า ต้องผูกกับข้อมูล Database (`useRealtimeCollection('products')`) โดยตรง **บังคับ** ต้องแนบเงื่อนไข `.where('companyId', '==', currentCompanyId)` และ `.where('isDeleted', '==', false)` เสมอเพื่อป้องกันข้อมูลข้ามบริษัท และช่องค้นหาต้องมีระบบ Debounce (หน่วง 300ms) พร้อม Limit ผลลัพธ์สูงสุดไม่เกิน 50 รายการเพื่อป้องกันเบราว์เซอร์ค้าง นอกจากนี้ตอนกรอก/แสดงผลรหัสสินค้า จะต้องเช็คถึงฟิลด์ `sku` เสมอ (ห้ามเอา Firestore ID มาโชว์แทน SKU)
     - **Dropdown รหัส/ชื่อ:** หน้าต่างค้นหาตอนพิมพ์ ต้องแสดงรหัสสินค้าให้เห็นด้านบนของชื่อสินค้าเสมอ เพื่อยืนยันว่าเลือกถูก SKU และต้องมีขนาดกะทัดรัด (`max-h-[160px] py-1`)
     - **การพิมพ์ภาษาไทย (Tone Marks):** ทุกช่องที่ถูกบีบความสูง (เช่น `h-7`) ต้องบังคับใส่คลาส `py-0 leading-relaxed` เพื่อป้องกันไม้เอก/ไม้โท หรือสระถูกบัง/ตัดขอบ
     - **ตัวเลขและลูกน้ำ (Smart Comma):** ช่องตัวเลข (จำนวน, ราคา) ต้องโชว์รูปแบบที่มีลูกน้ำ (,) ตลอดเวลาแม้คลิกเข้าแถวนั้น และจะหลุดเป็นตัวเลขดิบเฉพาะวินาทีที่ "คลิกโฟกัสในช่องนั้น" เท่านั้น
     - **ระบบหน่วยอัจฉริยะ (Dynamic Units):** หากสินค้าที่เลือกมีหลายหน่วยอ้างอิง (Conversions) ช่องหน่วยจะแปลงร่างเป็น Dropdown ขนาดกะทัดรัด (native select `appearance-none`) ให้เลือกอัตโนมัติ 
     - **การนำทางด้วยคีย์บอร์ด และคอลัมน์การเงิน:** รองรับการกด `Enter` กระโดดไปยังช่องถัดไป (ชื่อ -> จำนวน -> หน่วย -> ราคา -> ส่วนลด -> ราคารวม) และสร้างแถวใหม่เมื่อ `Enter` ช่องสุดท้าย โดยช่องส่วนลดต้องรองรับทั้งรูปแบบเปอร์เซ็นต์ (%) และจำนวนเงิน (฿) ส่วนช่องราคารวมต้องเป็น Read-only ห้ามพิมพ์ ระบบคำนวณอัตโนมัติ
     - **การเตรียมพิมพ์ (Auto-Select):** ย้ายโฟกัสเข้าช่องตัวเลขต้องไฮไลต์ข้อความเดิมทั้งหมด (Select All) เสมอ
     - **ระบบคำนวณและป้องกันข้อมูล (Calculation Engine & Validation):** ทุกครั้งที่ช่อง จำนวน, ราคา หรือ ส่วนลด มีการเปลี่ยนแปลง (onChange) ต้องสั่งรันคำนวณราคารวมใหม่ และ Bubble up ผลลัพธ์กลับไปให้ Component แม่เพื่ออัปเดตยอดรวมทั้งเอกสารแบบ Real-time ห้ามผู้ใช้กรอกตัวเลขติดลบ (ยกเว้นส่วนลด) และหากผู้ใช้ลบจนช่องว่าง (Empty String) เมื่อเสียโฟกัสให้ระบบตั้งค่ากลับเป็น 0 หรือ 1 อัตโนมัติ เพื่อป้องกันการคำนวณพลาด (NaN)
     - ปุ่มเพิ่มลดตัวเลข (Spinner) ซ่อนโปร่งแสง ใช้ไอคอน `ChevronUp`/`ChevronDown` และทำงานต่อเมื่อเมาส์ชี้ช่องนั้นๆ 
     - ปุ่มรายละเอียดแบบ Toggle ย้ายไว้ท้ายสุดของช่องชื่อ (ไอคอน `AlignLeft`) เมื่อเปิดจะหล่นใต้แถวเดิม (Accordion)
     - **ปุ่มถังขยะ:** จับแยกเป็นคอลัมน์ริมสุดของตัวเองแบบบีบความกว้างให้พอดีไอคอนเป๊ะๆ (เช่น `w-5` แบบไม่มี Background สีดำ) เพื่อให้คอลัมน์ยอดรวมชิดขวาได้อย่างสมบูรณ์แบบ
  3. **การออกแบบ UI และพฤติกรรม (Aesthetics & UX)**:
     - **ระบบพับเก็บอัจฉริยะ (Click Outside):** ใช้ `capture: true` ไม่ให้ติด Event Bubble เมื่อคลิกนอกหน้าต่าง
     - ปุ่มถูก Disabled ไม่อนุญาตให้แก้ไขให้ใช้การลด Opacity (`pointer-events-none`) **ห้ามใช้** cursor Not-allowed วงกลมคาดแดง
     - ยอดสรุปจำนวนรายการที่ท้ายตาราง ให้ใช้ขนาดและสีแบบเดียวกับหัวตาราง
     - หัวตารางจัดชิดซ้าย/ขวาให้ตรงกับข้อมูล (ชื่อรายการชิดซ้าย, จำนวน/ราคาชิดขวา, รหัสกึ่งกลาง)
- **การปรับ UI และฟีเจอร์ต่างๆ ของตารางหลังจากนี้ ให้บันทึก/นำไปอัปเดตเป็นค่ากลาง (Central standard) ของคอมโพเนนต์ "ตารางอัจฉริยะ" (`DocumentItemsTable`) เสมอ** เพื่อให้ทุกหน้าที่เรียกใช้ตารางนี้ได้รับการอัปเดตฟีเจอร์และ UI ไปในทิศทางเดียวกันทั้งหมด

- **มาตรฐานฟีเจอร์และ UI ของตารางอัจฉริยะ (DocumentItemsTable) อัปเดตล่าสุดตาม PSG UI Protocol V3.1 (Edge Cases & Aesthetics):**
  1. **การเชื่อมต่อฐานข้อมูลและการดึงข้อมูลอัตโนมัติ:** ช่องรหัสสินค้า (SKU/Code) และช่องค้นหา ต้องเชื่อมต่อตรงกับ Firestore Collection `products` ผ่านฟังก์ชัน `useRealtimeCollection` พร้อมแนบเงื่อนไข Strict Tenant Isolation `.where('companyId', '==', companyId)` และ `.where('isDeleted', '==', false)` ทุกครั้ง เมื่อเลือกสินค้า ระบบต้องทำ Auto-Fill ข้อมูล (ชื่อ, หน่วย, ราคาต่อหน่วย) ลงในแถวทันทีผ่านการทำ Batch Update (`updateItemFields`) เพื่อป้องกัน React Stale State
  2. **การควบคุมขนาด Component และการดัก Edge Cases (สำคัญมาก):**
     - **แถวข้อมูลปกติ (Inline Rows):** บังคับความสูงขั้นต่ำ `min-h-[36px]` (h-9) และคุมฟอร์ม Input ให้เป็นทรงแคปซูล `rounded-full`
     - **แถวเมื่อไม่มีข้อมูล (Empty State / Placeholder):** ห้ามใช้ Padding ใหญ่ (เช่น py-8) เด็ดขาด! ต้องใช้ `min-h-[36px] flex items-center justify-center` ให้มีความสูงกะทัดรัดเท่ากับแถวปกติทุกประการ
     - **การจัดการ Input ตัวเลข (Spin Buttons Reset):** ช่องกรอกจำนวนและราคา บังคับใส่คลาสซ่อมแซมเบราว์เซอร์ `[appearance:textfield] [&::-webkit-outer-spin-button]:appearance-none [&::-webkit-inner-spin-button]:appearance-none` เพื่อป้องกันไม่ให้ปุ่มลูกศรของ Chrome/Edge โผล่มาซ้อนทับกับปุ่มแคปซูล Custom Stepper ทางขวามือ
     - **ช่องหน่วยนับและราคา:** อนุญาตให้ผู้ใช้คลิกพิมพ์แก้ไขเปลี่ยนแปลงค่าได้อิสระ
  3. **การจัดวางสัดส่วนคอลัมน์ (Column Layout & Actions):**
     - คอลัมน์รหัส, จำนวน, หน่วย, ราคา ให้ปรับขนาดพอดีข้อมูล (Fit-to-content) และช่องจำนวนกำหนดความกว้างพอดี (เช่น `w-24`) ไม่ให้ยาวเกินไป
     - คอลัมน์ชื่อรายการสินค้า ให้ขยายเต็มพื้นที่ที่เหลือ (`flex-1` หรือ `w-full`) เพื่อความยืดหยุ่นในการพิมพ์
     - ปุ่มลบรายการ (Delete Action) ในช่องสุดท้าย ให้เป็นไอคอนถังขยะขนาดเล็กกะทัดรัด แสดงผลเฉพาะตอนเมาส์ชี้ (Hover) เพื่อลดสัญญาณรบกวนทางสายตา (Noise) และป้องกันแท็บ Dropdown โดนบังโดยต้องปรับให้ `z-index` ของหน้าต่างหรือกล่องข้อความอยู่หน้าสุดเสมอ
  4. **กฎเหล็ก UI และ Typographical Constraints:**
     - **ธีม:** Sci-Fi Aesthetic (Dark Theme ตัดกับขอบสี Cyan)
     - **ฟอนต์ตัวเลขและผลรวมทั้งหมด:** บังคับใช้ฟอนต์ Monospace (`font-mono text-right`) และ **ห้ามมีตัวเอียง (Non-italic Policy 0%)** เด็ดขาด
  1. **ช่องข้อมูลที่ว่างเปล่า (Empty/Unselected State):** หากช่องกรอกข้อมูล หรือ Dropdown ยังไม่มีการคีย์หรือเลือกข้อมูล ตัวหนังสือจะต้องแสดงผลแบบสีไม่เด่น (เช่น `text-white/40 font-normal`) แต่เมื่อมีการคีย์หรือเลือกแล้วจึงจะเปลี่ยนเป็นสีสว่าง (`text-white font-bold`)
  2. **ช่องกรอกวันที่ (Date Input):** ให้ใช้เป็น Text Input พร้อมระบบ Masking (เช่น `maskType="date"` หรือดักใน Component) เพื่อให้ผู้ใช้สามารถพิมพ์ตัวเลขรัวๆ ได้ทันทีตามฟอร์แมต `DD/MM/YYYY` โดยไม่ต้องกดผ่าน Calendar Popup แบบเดิม
  3. **การบังคับจำนวนอักขระ (Input Mask & Length Limit):** ช่องที่มีรูปแบบตายตัว (เช่น เลขบัตรประชาชน 13 หลัก, เบอร์โทรศัพท์, เลขบัญชี, วันที่) ต้องมีการทำ Real-time Masking โดยตัด (Slice) ค่าที่รับเข้ามาให้อยู่ในความยาวที่ถูกต้องเสมอที่ระดับ Data (ก่อนนำไปจัดฟอร์แมต) และต้องตั้งค่า `maxLength` ใน HTML ให้ครอบคลุมจำนวนอักขระรวมสัญลักษณ์ขีดคั่นเสมอ เพื่อป้องกันไม่ให้ผู้ใช้พิมพ์ตัวอักษรส่วนเกินเข้าไปได้ตั้งแต่แรก
  4. **Dropdown อัจฉริยะ:** ช่อง Dropdown ทั้งหมดต้องรองรับการค้นหา (Search) ในตัว และข้อความที่ยาวเกินไปในรายการตัวเลือกต้องถูกปัดบรรทัด (Text Wrapping) ให้อ่านได้ครบถ้วน
- **มาตรฐานและฟีเจอร์ของช่องกรอกข้อมูลและ Dropdown (`NexusInput`, `PillInput`, `NexusSelect`, `PillSelect`, `NexusDatePicker`)** ที่ต้องยึดเป็นค่ากลางเสมอ:
  1. **ช่องข้อมูลที่ว่างเปล่า (Empty/Unselected State):** หากช่องกรอกข้อมูล หรือ Dropdown ยังไม่มีการคีย์หรือเลือกข้อมูล ตัวหนังสือจะต้องแสดงผลแบบสีไม่เด่น (เช่น `text-white/40 font-normal`) แต่เมื่อมีการคีย์หรือเลือกแล้วจึงจะเปลี่ยนเป็นสีสว่าง (`text-white font-bold`)
  2. **ช่องกรอกวันที่ (Date Input):** ให้ใช้เป็น Text Input พร้อมระบบ Masking (เช่น `maskType="date"` หรือดักใน Component) เพื่อให้ผู้ใช้สามารถพิมพ์ตัวเลขรัวๆ ได้ทันทีตามฟอร์แมต `DD/MM/YYYY` โดยไม่ต้องกดผ่าน Calendar Popup แบบเดิม
  3. **การบังคับจำนวนอักขระ (Input Mask & Length Limit):** ช่องที่มีรูปแบบตายตัว (เช่น เลขบัตรประชาชน 13 หลัก, เบอร์โทรศัพท์, เลขบัญชี, วันที่) ต้องมีการทำ Real-time Masking โดยตัด (Slice) ค่าที่รับเข้ามาให้อยู่ในความยาวที่ถูกต้องเสมอที่ระดับ Data (ก่อนนำไปจัดฟอร์แมต) และต้องตั้งค่า `maxLength` ใน HTML ให้ครอบคลุมจำนวนอักขระรวมสัญลักษณ์ขีดคั่นเสมอ เพื่อป้องกันไม่ให้ผู้ใช้พิมพ์ตัวอักษรส่วนเกินเข้าไปได้ตั้งแต่แรก
  4. **Dropdown อัจฉริยะ:** ช่อง Dropdown ทั้งหมดต้องรองรับการค้นหา (Search) ในตัว และข้อความที่ยาวเกินไปในรายการตัวเลือกต้องถูกปัดบรรทัด (Text Wrapping) ให้อ่านได้ครบถ้วน

- **กฎเหล็กของการพัฒนาระบบ (Strict Rule):** ห้ามแก้ไขโค้ดส่วนอื่นใดที่ไม่ได้สั่ง และห้ามแตะต้องหน้าอื่นๆ ที่ไม่ได้อยู่ในการ Focus การปรับปรุง (ยกเว้นส่วนที่เกี่ยวข้องกันโดยตรง หรือโค้ดกลางที่ต้องปรับเพื่อให้เข้ากันภายใต้กฎการออกแบบของระบบเท่านั้น)

- **เครื่องหมายบังคับกรอก (Required Field):** ต้องใช้เครื่องหมาย `*` สีแดง 100% (`<span className="text-red-500 font-bold">*</span>`) เสมอในทุกๆ จุดของระบบ เพื่อให้เป็นมาตรฐานเดียวกันทั้งหมด

- **กฎการแสดงผลรหัสเอกสาร/รหัสอ้างอิง (Document Code Colors):** 
  1. **รหัสหลักของหน้า (Primary Code):** ให้ใช้สีประจำระบบ (เช่น `text-nexus-teal font-mono font-bold`) เพื่อให้เด่นชัดที่สุดว่าเป็นเอกสารอะไร
  2. **รหัสอ้างอิง (Reference Code):** ให้ใช้สีที่แตกต่างออกไป (เช่น `text-blue-400 font-mono` หรือสีที่กำหนดไว้) เพื่อให้ผู้ใช้แยกแยะได้ทันทีว่าอันไหนคือรหัสหลัก อันไหนคือรหัสที่ถูกดึงมาอ้างอิง
  3. **รูปแบบรหัส (Code Format):** การสร้างหรือแสดงฟอร์แมตรหัสเอกสาร จะต้องเขียนโค้ดให้ดึงค่า/รูปแบบ (Prefix/Format) มาจาก "หน้าตั้งค่าระบบ (Settings)" เสมอ ห้าม Hardcode รูปแบบรหัสตายตัวไว้ในหน้าเอกสารเด็ดขาด

- **มาตรฐานปุ่มกด (Button Standards):** 
  1. ปุ่มที่มีหน้าที่เดียวกันจะต้องใช้สไตล์ สี และไอคอนเหมือนกันทั้งระบบ (เช่น ปุ่ม "บันทึก/สร้าง" ต้องเป็นสีประจำระบบหรือ `bg-nexus-teal`, ปุ่ม "ยกเลิก" เป็นสีเทา/ขาวโปร่งแสง, ปุ่ม "ลบ" เป็นสีแดง) เพื่อให้ผู้ใช้เกิดความคุ้นเคยและเป็น UI UX มาตรฐานเดียวกัน
  2. **ขนาดตัวอักษรบนปุ่ม (Button Font Size):** ให้ใช้ขนาดมาตรฐานของ Component (เช่น `text-[13px]`) เสมอ ห้ามแทรกคลาส `text-xs`, `text-sm` หรือ `text-base` เพื่อทับซ้อนขนาดตัวอักษรของปุ่มอีก เพื่อรักษาให้ขนาดปุ่มเท่ากันทั้งระบบ

- **กฎการออกแบบปุ่ม, แท็บ, และโมดูล (Translucent Glassmorphism):** 
  1. ส่วนที่ถูกเลือก (Active state) หรือปุ่มหลัก (Primary, Save, Confirm, Warning, Danger) **ห้ามใช้สีพื้นหลังทึบ (Solid color)** เด็ดขาด
  2. ให้ใช้เทคนิคกระจกโปร่งแสง (Translucent) เสมอ โดยประกอบด้วย:
     - พื้นหลังโปร่งแสง: `bg-[สี]/20`
     - สีตัวหนังสือสว่าง: `text-[สี]`
     - กรอบโปร่งแสง: `border border-[สี]/30`
     - เอฟเฟกต์เบลอ: `backdrop-blur-md`
     - ตัวอย่าง (ปุ่มหลัก): `bg-nexus-teal/20 text-nexus-teal border border-nexus-teal/30 backdrop-blur-md`

- **กฎการรักษามาตรฐานหน้าจอ (UI/UX Lock):** ห้ามแก้ไข เปลี่ยนแปลง หรือลบการเชื่อมโยงลิงก์ (Routing) ของหน้าเพจที่ถูกเปลี่ยนจากการใช้ Modal ไปเป็นหน้าเพจแบบเต็ม (Full-page) เด็ดขาด (เช่น การแก้ปุ่มแก้ไขใบเสนอราคา/ลูกค้าให้ลิงก์ไปที่ /sales/quotations/new?id=... แทนการเปิด Modal) และให้ยึดรูปแบบ Layout และ Navigation นี้เป็นมาตรฐานสูงสุด หากไม่ได้มีคำสั่งให้เปลี่ยน ห้ามแก้ไขกลับไปใช้รูปแบบเดิมเด็ดขาด

- **กฎการแปลงข้อมูลข้ามเอกสาร (Data Mapping Lock):** เมื่อมีการดึงข้อมูลจากเอกสารหนึ่งไปสร้างอีกเอกสารหนึ่ง (เช่น ดึง Quotation ไปสร้าง Project) จะต้องทำ Data Mapping ของตารางสินค้า (DocumentItemsTable) ให้ครอบคลุมทั้งรูปแบบเก่าและใหม่เสมอ (เช่น productId: item.productId || item.sku, qty: item.qty || item.quantity, price: item.price || item.unitPrice, unit: item.unit || 'ชิ้น') และต้องแปลง id ให้เป็นตัวเลข (Date.now() + index) เสมอเพื่อป้องกัน Error เรื่อง key นอกจากนี้ฟิลด์ข้อความที่เป็น Default (เช่น 	itle ที่เป็น 'ใบเสนอราคา') จะต้องถูกกรองทิ้ง (เว้นว่าง) เพื่อไม่ให้แสดงเป็นชื่อโครงการ/เอกสารผิดประเภท

- **กฎเหล็กของการพัฒนาระบบ (Strict Rule):** ห้ามแก้ไขโครงสร้าง รูปแบบการทำงาน UX/UI การเชื่อมโยงลิงก์ (Routing) และหน้าเพจที่ไม่ได้สั่งยกเว้นส่วนที่เกี่ยวข้องกันโดยตรง
- **ระบบถามก่อนทำ (Ask First):** หากคำสั่งใหม่มีความเสี่ยงที่จะละเมิดกฎที่มีอยู่ หรือเปลี่ยนรูปแบบที่ทำไว้แล้ว ให้ **"สอบถามผู้ใช้ก่อนเสมอ"** ห้ามคิดหรือตัดสินใจเปลี่ยนเองโดยเด็ดขาด
- **การรักษาฐานข้อมูล (Database Safety):** การเชื่อมโยงฐานข้อมูล (Firebase/Firestore) ที่ถูกตั้งค่าและทำงานได้อย่างถูกต้องแล้ว ต้องใช้ความระมัดระวังสูงสุด ห้ามปรับเปลี่ยนโดยพลการ

- **กฎการปรับแต่ง UI เป็นค่ากลางและปกป้องฟีเจอร์เฉพาะ (Global UI Standardization & Safe-Update):**
  ทุกครั้งที่ผู้ใช้สั่งให้ปรับแต่งองค์ประกอบ UI (เช่น การเปลี่ยนโทนสี, ขนาดอักษร, ระยะห่าง Padding/Margin, ความโค้งมน, เส้นขอบ, หรือเปลี่ยนชุดไอคอน) คุณต้องปฏิบัติตามกฎ "Zero-Interference" ดังนี้:
  - 🛑 Confirmation Rule (ถามก่อนแก้): คุณห้ามแก้ไขโค้ด UI เฉพาะเจาะจงแค่ในไฟล์หน้านั้นเพียงไฟล์เดียวเด็ดขาด! ให้คุณหยุดและถามผู้ใช้ก่อนเสมอว่า "ต้องการให้บันทึกการปรับแต่งนี้เป็น 'ค่ากลาง (Global UI Standard)' ลงในคลังแสง (เช่น SmartComponents หรือ Tailwind Config) เพื่อให้หน้าอื่นๆ ปรับเปลี่ยนตามด้วยหรือไม่?"
  - 🌍 Global Update: หากผู้ใช้ตอบตกลง (Yes) ให้คุณนำการตั้งค่า UI ใหม่นี้ ไปอัปเดตที่คอมโพเนนต์ส่วนกลาง (เช่น src/components/ui/) หรือไฟล์ Config กลางของระบบทันที และไม่ยุ่งกับส่วนที่ปรับปรุงเพิ่มมา(เช่นช่องค้นหาในตารางสินค้า มีการเชื่อมโยงกับรหัสสินค้า การดึงข้อมูลมาแสดงในช่องค้นหาต้องไม่ถูกลดทอน)
  - 🛡️ Zero-Interference Protocol (ห้ามทำฟีเจอร์อื่นพัง): การอัปเดต UI ไม่ว่าจะเป็นค่ากลางหรือเฉพาะหน้าจอ ห้ามไปแตะต้อง ลบ หรือลดทอน ฟังก์ชันการทำงาน (Business Logic), โครงสร้างฐานข้อมูล (Data Schema), ฟังก์ชันการคำนวณ, หรือความสามารถพิเศษอื่นๆ ที่ถูกพัฒนาขึ้นมาเฉพาะในคอมโพเนนต์นั้นๆ อย่างเด็ดขาด (อัปเดตเฉพาะสไตล์การแสดงผลเท่านั้น โค้ดส่วนสมองต้องอยู่ครบ 100%)

- **กฎการออกแบบปุ่ม (Button UI Protocol):** การสร้างหรือปรับแก้ปุ่ม (Button) ทุกครั้ง ให้บังคับใช้รูปแบบโปร่งใส (Glass/Transparent) (เช่น variant="glass") และให้ AI พิจารณากำหนดโทนสีให้สอดคล้องกับ หน้าที่การทำงาน (Function) เช่น ปุ่มบันทึก/ยืนยันให้ใช้โทนสีหลัก/สีเขียว (เช่น text-nexus-teal border-nexus-teal/30 hover:bg-nexus-teal/10), ปุ่มยกเลิก/ลบให้ใช้โทนสีแดง (เช่น text-red-400 border-red-500/30 hover:bg-red-500/10), หรือปุ่มแก้ไข/ข้อมูลให้ใช้โทนสีน้ำเงิน/รอง (เช่น text-blue-400 border-blue-500/30 hover:bg-blue-500/10) โดยยังคงรักษาดีไซน์โปร่งใส (Glass) ไว้เสมอ และห้ามใช้ปุ่มสีทึบเด็ดขาด

- **มาตรฐานฟอร์มข้อมูลส่วนหัว (Document Header Form UI/UX Standard):** หน้าต่างสร้าง/แก้ไขเอกสารทุกประเภท (เช่น ใบเสนอราคา, ใบสั่งขาย, ใบกำกับภาษี) ต้องยึดถือรูปแบบการแสดงผลและช่องกรอกข้อมูลต่อไปนี้เป็นค่ากลาง (Central standard):
  1. **ช่องกรอกข้อมูลกะทัดรัดขั้นสุด (Extreme Compact Header Inputs):** ช่องกรอกข้อมูล (เช่น `PillInput`, `<select>`, `SmartSelect`) ทุกช่องในส่วน Header ของเอกสาร ต้องใช้ความสูงกะทัดรัดที่ระดับ `h-7 py-0 leading-relaxed` และขนาดตัวอักษร `text-[13px] font-bold` (ถ้าเป็นตัวเลข/รหัสให้บวก `font-mono tracking-tight`) เพื่อประหยัดพื้นที่หน้าจอให้มากที่สุด
  2. **ช่องค้นหาอัจฉริยะแบบฝังตัว (Inline Smart Combobox):** สำหรับช่องที่ดึงข้อมูลความสัมพันธ์ (เช่น ชื่อลูกค้า, รหัสสินค้า) ให้ใช้คอมโพเนนต์แบบค้นหาและพิมพ์ได้ในตัว (เช่น `AsyncCustomerSelect`, `AsyncProductSelect`) โดยใช้สไตล์พื้นฐาน `bg-white/[0.03] border border-white/10` และผู้ใช้ต้องสามารถพิมพ์ค้นหาด้วย ชื่อ หรือ รหัส ได้โดยตรงโดยไม่ต้องมีปุ่มค้นหาแยก
  3. **รูปแบบภาษีและตัวเลือก (Tax Display Mode & Toggles):** แถบตัวเลือกรูปแบบภาษีต้องเรียงลำดับจาก `[ ไม่มี VAT ] -> [ ก่อน VAT ] -> [ รวม VAT ]` เสมอ โดยให้ปุ่มมีความกว้างเท่าที่จำเป็น (`w-fit px-4`) ห้ามใช้ `flex-1` เพื่อยืดปุ่มจนเต็มบรรทัด
  4. **ช่องติ๊กเลือก (Inline Toggles):** ปุ่มเปิดปิดเงื่อนไข (เช่น "รวม VAT ในราคาสินค้า") ให้จัดเรียงต่อท้ายในบรรทัดเดียวกันกับตัวเลือกที่เกี่ยวข้อง (`flex-col xl:flex-row items-start xl:items-center`) ไม่ปัดบรรทัดใหม่ และใช้รูปแบบแคปซูลโปร่งแสง แทน Checkbox ธรรมดา

- **การพัฒนาระบบใบเสนอราคา (Quotation):** ล็อกการพัฒนาหน้าสร้าง/แก้ไขใบเสนอราคา (เช่น /sales/quotations/new/page.tsx) อนุญาตให้ เพิ่ม การพัฒนาและฟีเจอร์ได้เท่านั้น **ห้ามลบข้อมูล ฟิลด์ โค้ด หรือลบความสามารถใดๆ ออกเด็ดขาด** หากมีคำสั่งจากผู้ใช้ที่ทำให้ต้องมีการลบ หรือปรับโครงสร้าง/แก้ไขครั้งใหญ่ (Major Refactor) จะต้องหยุดทำงาน แจ้งเตือน และสอบถามผู้ใช้เพื่อขออนุมัติอย่างชัดเจนก่อนเสมอ

- **กฎการออกแบบหน้า UI ของระบบ (Full-Page Data Entry Protocol):** ให้ออกแบบเป็นหน้าเพจบันทึกข้อมูลแบบเต็มหน้าจอ (Full-Page Data Entry) เท่านั้น ห้ามใช้หน้าต่าง Modal หรือ Overlay เด็ดขาด (ยกเว้นจะได้รับคำสั่งเป็นพิเศษเฉพาะจุดๆ ไป) เพื่อรองรับความซับซ้อนของข้อมูลสเกล Enterprise, Split Layout และเพื่อลดความเสี่ยงที่ข้อมูลจะสูญหายจากการปิด Modal โดยไม่ตั้งใจ

  3. ปุ่มไอคอน (Icon Action Buttons) บังคับใช้ขนาดทรงกลมมาตรฐาน: `w-9 h-9 rounded-full flex items-center justify-center`
